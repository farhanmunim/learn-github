GitHub, explained for people who build things

More than forty short chapters that teach you how to use Git and GitHub properly, whether you work alone, with a team, or with an AI assistant writing half the code. Each one takes two or three minutes and most end with a line you can say out loud.

Start with the journey below. It is the loop almost every change goes through, from an idea on your laptop to code that is live. Once you can narrate this loop, you can follow most conversations about how a team works in GitHub.

The parts

Git is the tool that tracks your code's history. GitHub is a website that hosts Git projects and adds teamwork on top.

Git is free software that runs on your computer. It remembers every version of every file in a project, so you can see what changed, when, and why, and go back if something breaks. It works completely offline and has nothing to do with any website.

GitHub is a company's website (owned by Microsoft) that stores copies of Git projects online. On top of the storage it adds things Git doesn't have: accounts, a web page for each project, issues (a to-do and bug list), pull requests (a way to propose and review changes), automation, and permission controls. Similar services exist: GitLab, Bitbucket, Codeberg. They all speak Git; the extras differ.

Two benefits make it worth learning even if you work alone: history (an undo button for your whole project, not just one file) and backup (your laptop can die and your work is still on GitHub). With a team, you also get a shared place where everyone's work meets without overwriting each other.

In your project

If you've ever kept files called final, final-v2 and final-REALLY, Git replaces all of that with one folder and a searchable history.

Say it like this

"Git is the tool, GitHub is where we host it. I can commit offline and push when I'm back online."

Four nouns you'll hear in almost every Git sentence.

A repository (or repo) is a project folder plus its full history. Git keeps the history in a hidden folder called .git. Delete that folder and the project becomes ordinary files again, so never touch it by hand.

A commit is a saved snapshot of your project at one moment, with a message saying what changed, an author and a timestamp. Each commit has an ID, a long string of letters and digits called a hash (for example a1b2c3d when shortened). Commits form a chain, each pointing at the one before it. That chain is the history.

A branch is a movable label pointing at a commit, in effect a separate line of work. The main line is usually called main. You create other branches for features and fixes, then bring them back in.

A remote is another copy of the repo somewhere else, usually on GitHub. By convention the main remote is named origin. Your own copy is the local repo; GitHub's copy is the remote.

Two more you'll see straight away: clone means downloading a full copy of a repo, and HEAD means "the commit you're currently looking at", which is normally the tip of the branch you're on.

Say it like this

"I cloned the repo, made a branch, committed twice and pushed it to origin."

Twenty minutes of setup now saves you from lockouts and embarrassing commits later.

1. Create your account and turn on two-factor authentication. Your GitHub account can publish code that other people run, so it's a target. Enable 2FA in Settings, then Password and authentication. A passkey (a login stored on your phone or laptop that replaces the password) or an authenticator app is better than text messages. Save the recovery codes somewhere safe, such as a password manager.

2. Install Git and tell it who you are. Every commit carries a name and email:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

If you don't want your real email in public commits, GitHub gives you a private one under Settings, then Emails ("Keep my email addresses private"). It looks like 12345+username@users.noreply.github.com; use that as user.email.

3. Choose how your computer proves who it is to GitHub. GitHub no longer accepts your account password for Git commands. Pick one:

  • GitHub CLI (gh auth login): the easiest path. It signs you in via the browser and sets up HTTPS credentials for you.
  • HTTPS with a credential manager: Git for Windows and macOS bundle one that opens a browser sign-in the first time.
  • SSH key: you generate a key pair with ssh-keygen -t ed25519, add the public half (.pub file) to Settings, then SSH and GPG keys, and never type a credential again. The private half never leaves your machine.

A personal access token (PAT) is a long password-like string with limited powers, used by scripts and tools. Treat it like a password: never paste it into code, chats or screenshots.

Careful

"Anything that can push to your account can change your code." Don't store tokens in a file inside a repo, and don't share your screen with a terminal showing one.

Say it like this

"I've got 2FA and an SSH key set up, and my commits use the noreply address so my email isn't public."

There are two ways to start: create a repo from scratch, or clone one that already exists.

Starting from scratch. Go into your project folder and turn it into a repo:

cd my-project
git init
git add .
git commit -m "Initial commit"

That's a repo with one commit. To put it on GitHub, create an empty repository on the website (no README, so nothing conflicts), then connect and upload:

git remote add origin git@github.com:you/my-project.git
git push -u origin main

The -u remembers that your local main goes with origin/main, so later a bare git push or git pull just works. With the GitHub CLI, gh repo create does all of this in one step.

Starting from an existing repo. Use clone. It downloads everything, history included, and sets up origin for you:

git clone git@github.com:someone/their-project.git

On the repo's page, the green Code button shows the address to copy. HTTPS addresses start with https://, SSH ones with git@github.com:. Use whichever matches your setup.

In your project

Create the repo on GitHub on day one, even for a weekend experiment. It's free, private repos are fine, and it means your first working version is already backed up.

Say it like this

"Just clone it and run the install, the README says what to do."

Git has a waiting room between your edits and your history, and understanding it clears up most early confusion.

Your files live in three states, and a change moves through them in order:

  • The working tree (or working directory) is the actual files you edit. Changes here are not yet recorded anywhere.
  • The staging area (or index) is a list of the changes you've chosen to include in the next commit. git add puts changes there.
  • The repository holds committed snapshots. git commit turns whatever is staged into a permanent commit.

Why the middle step? So one commit can hold exactly one idea. You might have edited five files while fixing a bug and tidying a heading; staging lets you commit the bug fix first and the tidy-up separately.

Useful variants: git add -p lets you pick individual chunks within a file, and git commit -a skips staging for files Git already tracks (it won't pick up brand-new files).

Say it like this

"Stage the fix on its own, I don't want the formatting changes in the same commit."

A good commit is small, does one thing, and has a message your future self can understand.

Commit often. A commit is a save point, and cheap. Small commits are easy to review, easy to undo and easy to find bugs in. A commit called "stuff" that changes forty files is none of those.

One idea per commit. People call this an atomic commit. If you can't describe it without the word "and", it's probably two commits.

Write the message for a stranger. The convention is a short summary line (about 50 characters, in the imperative: "Fix login redirect", not "Fixed" or "Fixes"), then, if needed, a blank line and a longer explanation of why. The diff already shows what changed; the message should say why.

git commit -m "Fix redirect loop after login" -m "The session cookie was set after the redirect, so the next request looked logged out."

Many teams use Conventional Commits, a light naming scheme that starts the summary with a type, such as feat:, fix:, docs: or chore:. It makes history scannable and lets tools generate changelogs. Whether you adopt it matters less than being consistent.

  • Don't commit broken code to a shared branch if you can help it. Test first.
  • Don't mix formatting with logic. Reformatting a file in the same commit as a bug fix hides the fix.
  • Fix the last commit with git commit --amend, but only if you haven't pushed it yet.

In your project

Commit every time something works, even tiny. When an AI tool or a late-night edit breaks things, you'll be one command away from the last good state.

Say it like this

"Can you split that into two commits? The refactor and the bug fix are tangled together."

Three read-only commands tell you where you are before you change anything.

git status        # what's changed, what's staged, which branch am I on
git diff          # exact line changes not yet staged
git diff --staged # exact line changes that are staged
git log --oneline --graph --decorate -15

git status is the one to run constantly. It also tells you what to do next ("Changes not staged for commit", "Your branch is ahead of 'origin/main' by 2 commits").

A diff shows changes line by line: lines starting with - were removed and lines starting with + were added. Reading your own diff before every commit is the single best habit for catching leftovers like debug prints, stray files and secrets.

git log lists commits, newest first. The options above squash it to one line each and draw the branch shape. Add -p to see each commit's changes, or a filename (git log -- path/to/file) to see one file's history.

Two forensic tools worth knowing: git blame file shows who last changed each line (and the commit to ask about it), and git show a1b2c3d shows one commit in full. On GitHub, the History and Blame buttons on a file do the same thing.

Say it like this

"Run git status and git diff first, I want to see what's actually changed before we commit."

Nearly everything in Git can be undone, as long as you know which undo matches which situation.

SituationCommand
Throw away edits to a file (not yet staged)git restore file
Unstage a file but keep the editsgit restore --staged file
Fix the last commit's message or contents (not pushed yet)git commit --amend
Undo a commit that's already shared, safelygit revert a1b2c3d
Move a local branch back, keeping the changesgit reset --soft HEAD~1
Move a local branch back and discard the changesgit reset --hard a1b2c3d
Find a commit you think you lostgit reflog

The key distinction is revert versus reset. git revert adds a new commit that cancels an earlier one, so history is preserved and it's safe on shared branches. git reset moves the branch pointer and (with --hard) throws work away; use it only on commits nobody else has.

The safety net is the reflog, a private log of everywhere your HEAD has been. If you reset too far, git reflog shows the commit you were on a minute ago, and git reset --hard HEAD@{1} returns to it. Commits you've made are very hard to lose; edits you never committed are not recoverable, which is another reason to commit often.

Careful

git restore file and git reset --hard permanently delete uncommitted work. Run git status and make sure you mean it.

Say it like this

"Don't reset main, it's already pushed. Revert the commit and we'll keep the history honest."

Some files should never be in a repo: secrets, dependencies, build output and your editor's clutter.

A file called .gitignore in your repo root lists patterns Git should pretend don't exist. Typical entries:

# dependencies and build output
node_modules/
dist/
.next/

# secrets and local config
.env
.env.*
!.env.example

# operating system and editor noise
.DS_Store
.vscode/

Why these? Dependencies (node_modules) are huge and can be recreated from package.json. Build output can be regenerated. Secrets such as API keys must never be in a repo (see the next chapter). The !.env.example line is an exception: a template file with fake values, so teammates know which settings are needed.

GitHub can create a .gitignore for your language when you make a repo, and the github/gitignore project on GitHub holds templates for everything.

Careful

.gitignore only affects files Git isn't tracking yet. If you committed .env before adding it, run git rm --cached .env and commit. And the secret is still in your history; see the next chapter.

Say it like this

"Add dist and .env to the gitignore, and commit an .env.example so people know what to set."

If a password or API key lands in a commit, assume it's compromised and rotate it, don't just delete it.

A secret is any credential: API keys, database passwords, tokens, private keys. Bots scan public GitHub constantly and can find a leaked key within minutes, so speed matters.

Why deleting the file isn't enough: Git remembers. The secret stays in older commits, in forks, in clones and in any cached views. Removing it from the latest version only hides it from casual view.

  1. Revoke or rotate the secret first. Generate a new key in the provider's dashboard and disable the old one. This is the step that actually fixes the problem.
  2. Put the new one somewhere safe: an .env file that's gitignored, or your host's secret settings.
  3. Optionally clean the history with a tool such as git filter-repo, then force-push. This is tidying, not protection, and it's awkward on shared repos.

Prevention beats cleanup. GitHub's secret scanning looks for known key formats and alerts you, and push protection blocks a push containing one (it's on by default for public repos and can be switched on for private ones). Many tools you'll meet say "never commit .env"; this is why.

In your project

Anything the browser can see is public. If an API key ends up in front-end code, it's leaked no matter what your repo says, so keep keys on a server or in a function.

Say it like this

"We pushed a key to a public repo. Rotate it first, then we'll worry about scrubbing history."

A branch is a safe side-road: work there can't break main until you choose to merge it.

Under the hood a branch is just a label pointing at a commit, which is why creating one is instant and costs nothing. Make one for every feature, fix or experiment.

git switch -c feature/login   # create and move to a new branch
git switch main               # go back
git branch                    # list local branches
git branch -d feature/login   # delete a merged branch

(You'll also see git checkout in older guides. It does the same jobs but mixes several unrelated things; switch and restore are the clearer modern commands.)

When you switch branches, Git rewrites the files in your folder to match that branch. Commit or stash your changes first, otherwise Git may refuse or carry them across.

In your project

Even solo, branch before any risky change, such as a big redesign or letting an AI tool loose. If it goes badly, you delete the branch and main is untouched.

Say it like this

"Branch off main, do it on there, and we'll open a PR when it's ready."

Your local repo and GitHub only talk when you tell them to, and three commands cover almost all of it.

  • push uploads your local commits to a remote branch: git push.
  • fetch downloads new commits from the remote but doesn't change your files: git fetch. It's always safe.
  • pull is fetch followed by merging the new commits into your current branch: git pull.

The first push of a new branch needs to say where it goes: git push -u origin feature/login. After that, plain git push is enough.

Git keeps a local bookmark of where each remote branch was the last time you looked, named origin/main, origin/feature/login and so on. These are called remote-tracking branches. git status uses them to say "ahead by 2" or "behind by 1".

If a push is rejected ("non-fast-forward", "fetch first"), it means the remote has commits you don't. Pull, resolve anything needed, push again. Don't reach for --force (more on that in the errors chapter).

Build the habit: pull before you start work, push when you finish a chunk. Unpushed commits exist only on your laptop.

Say it like this

"Fetch first and see what's changed upstream, then rebase onto it before you push."

Both bring one branch's work into another; they differ in how the history looks afterwards.

Merge ties two branches together with a new merge commit. Nothing is rewritten; the history shows exactly what happened, including that the work happened in parallel.

git switch main
git merge feature/login

If main hasn't moved since you branched, Git just slides the pointer forward, called a fast-forward, and no merge commit is needed.

Rebase takes your branch's commits and replays them on top of the latest main, as if you'd started from there. The result is a straight line with no merge commit, but your commits get new IDs, because they now have different parents.

git switch feature/login
git rebase main

The golden rule: never rebase commits other people already have. Rewriting shared history forces everyone else to untangle their copies. Rebase your own unpushed or private branch freely; leave shared branches alone.

MergeRebase
HistoryPreserved, with merge commitsLinear, tidy
Rewrites commits?NoYes
Safe on shared branches?YesNo
Good forCombining finished workUpdating your own branch with the latest main

In your project

If you're unsure, merge. A slightly messy history is harmless; a botched rebase can cost you an afternoon.

Say it like this

"I'll rebase my branch onto main to pick up the latest, but I won't touch it once the PR is under review."

A conflict just means two people changed the same lines and Git needs a human to choose.

Git merges automatically when changes touch different parts of a file. When both sides edited the same lines, it stops and marks the file:

<<<<<<< HEAD
const title = "Welcome back";
=======
const title = "Hello again";
>>>>>>> feature/greeting

Everything between <<<<<<< HEAD and ======= is your side (the branch you're on), and the part up to >>>>>>> is theirs. To resolve it:

  1. Open the file and decide: keep yours, keep theirs, or combine them.
  2. Delete all the marker lines (<<<<<<<, =======, >>>>>>>) so only real code remains.
  3. Run the app or tests to check it still works.
  4. git add file, then git commit (or git rebase --continue if you were rebasing).

Stuck? git merge --abort (or git rebase --abort) puts everything back as it was. VS Code and GitHub's web editor both show conflicts with clickable "Accept current / incoming" buttons, which are friendlier than editing raw markers.

You'll hit fewer conflicts if branches are short-lived, PRs are small and you pull main into your branch regularly.

Say it like this

"There's a conflict in the config file. Keep both settings, I'll resolve it and push."

Three little commands that rescue you from awkward moments.

Stash shelves your uncommitted changes so you can do something else. Typical use: you're mid-edit and need to switch branches.

git stash          # put changes aside, working tree is clean again
git switch other-branch
# ...do the other thing, come back...
git stash pop      # bring the changes back

A tag is a permanent label on one commit, usually marking a release such as v1.2.0. Unlike a branch it doesn't move.

git tag v1.0.0
git push origin v1.0.0

cherry-pick copies a single commit from one branch onto another: git cherry-pick a1b2c3d. It's handy when a fix landed on the wrong branch, or you need one fix on an older release.

Say it like this

"Stash that, switch to main and cut the hotfix, then pop the stash when you're back."

A branch name should tell a stranger what the work is, and branches should die soon after they're born.

The default branch is where finished work ends up. GitHub now calls it main for new repos (older ones may still say master). Treat it as always-working and deployable.

Feature branches are the short-lived ones. Common naming patterns:

  • feature/login-page for new things
  • fix/cart-total-rounding for bugs
  • chore/update-deps for housekeeping
  • Include an issue number if you have one: fix/123-cart-rounding

Use lowercase and hyphens, no spaces. Consistency matters more than the exact scheme.

Keep branches short-lived. The longer a branch lives, the further it drifts from main and the worse the conflicts. A day or two is great; a month is a warning sign. Break big pieces of work into several smaller branches.

Clean up after merging. GitHub offers a Delete branch button once a PR merges (and a repo setting to do it automatically). The commits are safe in main, and you can restore a deleted branch from the PR page if you need to. Locally, git fetch --prune removes bookmarks for branches that no longer exist on the remote.

Say it like this

"That branch is three weeks old, rebase it or split it up before it becomes a conflict nightmare."

Every repo page has the same tabs, and knowing what each is for makes any project easy to navigate.

  • Code: the files, the branch picker, the green Code button (clone address) and the README shown underneath.
  • Issues: bugs, ideas and tasks.
  • Pull requests: proposed changes waiting for review.
  • Actions: automated workflows and their results.
  • Projects: boards for planning.
  • Security: vulnerability alerts, secret scanning and policy.
  • Insights: activity, contributors and dependency graphs.
  • Settings: visible only if you have admin rights. Visibility, access, branch rules, secrets and Pages live here.

A repo is either public (anyone on the internet can see it) or private (only people you invite). Public doesn't mean anyone can change it: only collaborators can push, and everyone else has to propose changes through forks and pull requests.

On the right of the Code tab you'll see About (description, website link, topics), Releases, Languages and the star and fork counts. A star is a bookmark and a thumbs-up. A watch subscribes you to notifications.

Handy keys on a repo page: press t to search files by name, . to open the repo in a browser-based editor, and ? to see all shortcuts.

Say it like this

"It's in the Actions tab, the last run failed on the lint step."

The README is your project's front door; the licence says what other people may do with it.

A README.md in the repo root is shown automatically on the repo page. It's written in Markdown, a simple way to write headings (#), lists (-), links and code blocks with plain text. A good README answers, in order:

  1. What is this? One or two sentences, and a screenshot if it's visual.
  2. How do I run it? The exact commands, from a fresh clone.
  3. How do I configure it? Which environment variables are needed (never the real values).
  4. How do I help? A link to the contributing guide, if there is one.

Test your README by following it on a clean machine, or asking someone else to. "Works on my machine" is the most common README bug.

A licence is a file (LICENSE) that says how others may use your code. With no licence, the default is "all rights reserved", which means nobody else may legally reuse it, even though it's visible. Common choices: MIT (do almost anything, keep the notice), Apache 2.0 (like MIT with a patent grant), GPL (derived work must also be open source). GitHub can add one for you when you create the repo, and choosealicense.com helps you decide.

Other files GitHub recognises: CONTRIBUTING.md (how to submit changes), CODE_OF_CONDUCT.md (expected behaviour) and SECURITY.md (how to report a vulnerability privately).

In your project

Write the README for yourself in six months. You will forget how to run your own project, and a five-line README saves you an hour.

Say it like this

"The README doesn't say which Node version it needs, can you add that to the setup section?"

An issue is a written record of something to do: a bug, a feature, a question.

Issues keep work out of people's heads and chat threads. Each has a number (#42), a title, a description, a comment thread and a status of open or closed. You can assign it to someone, tag it with labels (such as bug, enhancement, good first issue) and attach it to a milestone (a goal such as "v1.0").

A good bug report has:

  • What you expected and what happened.
  • Steps to reproduce, numbered, so anyone can see it for themselves.
  • Context: browser, version, operating system, error messages, a screenshot.

A good feature request explains the problem first, then a suggested solution. Maintainers can say yes to a clear problem even if they pick a different fix.

Two features make issues powerful. Mentions: typing #42 in any comment links to that issue, and @username notifies a person. Closing keywords: writing Fixes #42 in a pull request description closes the issue automatically when the PR merges to the default branch. Also works with Closes and Resolves.

Repos can add issue templates (in .github/ISSUE_TEMPLATE/) that give reporters a form to fill in, so you get the details you need.

In your project

Even alone, issues make a handy to-do list that links to the exact code change that finished each task. Write one when you have an idea mid-flow so you don't lose it.

Say it like this

"Can you open an issue with repro steps? I'll link the PR so it closes automatically."

A pull request is a conversation about a branch: "here's my change, please look before it joins main".

The name is a bit backwards: you're asking the owners to pull your changes into their branch. In practice, a PR is a page showing the difference between your branch and the target (the base), the commits, a place to discuss, and the results of automated checks.

To open one: push your branch, then click the yellow "Compare and pull request" banner on the repo page (or run gh pr create). Fill in:

  • A title that says what the change does.
  • A description: why it's needed, what changed, how you tested it, screenshots for visual work, and Fixes #42 to link the issue.

You can open a draft PR early to show work in progress and get feedback; it can't be merged until you mark it Ready for review. Any further commits you push to the branch appear in the same PR automatically.

Keep PRs small and focused. A 100-line PR gets a careful review; a 2,000-line one gets a nervous "looks good to me".

In your project

Working alone, open PRs against your own main anyway. You get a clean diff to read before merging, your checks run, and each PR becomes a labelled chapter in your project's story.

Say it like this

"Open a draft PR early so we can sanity-check the approach before you build the whole thing."

A review is a second pair of eyes on a change, and good ones are about the code, not the person.

On the PR's Files changed tab, you can click the + beside any line to leave a comment, or select several lines. When you've finished, submit the review with one of three verdicts:

  • Comment: feedback without a decision.
  • Approve: it's good to merge.
  • Request changes: something needs fixing first.

Reviewers can also write suggestions, small edits the author can accept with one click, which creates a commit for them. Conversations can be marked resolved once handled.

As a reviewer, check: does it do what the PR says? Is anything missing (tests, docs, edge cases)? Could it break something else? Could it leak a secret or open a security hole? Be specific, explain why, and separate must-fix from nitpicks ("nit: rename this if you like").

As the author, reply to each comment, push fixes and don't take it personally. Review is how a team keeps quality up and spreads knowledge.

Review AI-written code as hard as you'd review anyone's. It can look confident and be wrong.

Say it like this

"Approved with one nit, and I've left a suggestion on the error handling you can accept in one click."

GitHub's green button actually offers three ways of landing a PR, and each leaves different history behind.

MethodWhat lands on mainUse when
Create a merge commitAll the branch's commits plus a merge commit.You want a complete record of how the work happened.
Squash and mergeOne single commit containing the whole PR.The branch has messy "wip" commits and you want main to read as one commit per change. Popular default.
Rebase and mergeEach commit replayed on top of main, no merge commit.The commits are already clean and you want a straight line.

Repo admins can switch off the methods they don't want in Settings, so the button you see may offer fewer options.

After squashing, your branch's original commits aren't in main, so delete the branch afterwards, and don't carry on working on it. Start a fresh branch from the updated main.

Before merging, check three things: checks are green, review is approved, and the PR title reads well. With squash merging, the PR title becomes the commit message on main.

Say it like this

"Squash it, we don't need fourteen 'fix typo' commits in main."

A fork is your own copy of someone else's repo on GitHub, which lets you propose changes without needing permission to push.

On a public project you don't have write access. The workflow is:

  1. Fork it (the button at the top right). You now have you/project on GitHub.
  2. Clone your fork to your computer.
  3. Make a branch, commit and push to your fork.
  4. Open a pull request from your fork's branch to the original repo.

Your fork doesn't update by itself. Use the Sync fork button on your fork's page, or add the original as a second remote called upstream:

git remote add upstream https://github.com/original/project.git
git fetch upstream
git merge upstream/main

Etiquette for contributing: read CONTRIBUTING.md first, check existing issues, open an issue before doing a big piece of work so you don't waste a weekend on something they'd decline, keep PRs small, and be patient. Maintainers are often volunteers.

Say it like this

"I forked it, fixed the typo on a branch and sent a PR. I'll sync my fork before I make another one."

A workflow is just an agreement on how changes get from someone's laptop into main.

GitHub flow is the simplest and the most common, and the one this guide has been teaching:

  1. main is always deployable.
  2. For any change, branch off main with a descriptive name.
  3. Commit and push regularly.
  4. Open a pull request (a draft if it's early).
  5. Get review and green checks.
  6. Merge to main, delete the branch, deploy.

Trunk-based development pushes the same idea further: branches live for hours, not days, and unfinished features are hidden behind feature flags (switches in code that turn a feature on or off without redeploying). It suits teams with strong automated tests.

Gitflow is an older, heavier model with long-lived develop, release and hotfix branches. It still appears in teams that ship numbered versions on a schedule, but most web teams have moved to something simpler.

Whichever you use, the principles hold: protect main, keep changes small, review before merging, and let automation do the boring checking.

In your project

Start with GitHub flow. It scales from one person to a whole company, and you can add rules around it later.

Say it like this

"We do GitHub flow here: short branches off main, PR, review, squash, deploy."

Rules that stop anyone, including you on a tired Friday, from pushing straight to main or merging broken code.

Branch protection rules and their newer, more flexible cousin rulesets (Settings, then Rules or Branches) let you require things before a change can land on a branch. Typical set:

  • Require a pull request before merging, so nobody pushes directly to main.
  • Require approvals: for example one reviewer must approve.
  • Require status checks to pass: tests, lint and build must be green.
  • Require conversations to be resolved before merging.
  • Block force pushes and deletion of the branch.
  • Require linear history or signed commits, if your team wants them.

Rules apply to everyone unless you allow named people or roles to bypass. A sensible team has very few bypassers.

A status check is a pass or fail result reported by an automated job (usually GitHub Actions) onto a PR. A PR with a red cross can't be merged if that check is required.

Availability depends on your plan: rules work on public repos for free; private repos may need a paid plan, so check Settings if the options are missing.

In your project

Even solo, "require a PR and passing checks" on main is a cheap seatbelt, especially once AI tools or automation have push access.

Say it like this

"Main is protected, so you need a PR, one approval and green checks. No direct pushes."

Small files in your repo that route reviews to the right people and make every PR and issue consistent.

CODEOWNERS is a file (at .github/CODEOWNERS) that maps paths to people or teams. When a PR changes those files, GitHub automatically requests a review from the owner, and protection rules can require their approval.

# everything defaults to the core team
*            @acme/core-team
# payments code needs a payments reviewer
/payments/   @acme/payments
# docs can be reviewed by anyone on docs
*.md         @acme/docs

A pull request template (.github/pull_request_template.md) pre-fills the description box with headings you want filled in, for example "What changed", "How to test" and "Screenshots". Issue templates do the same for bug reports and requests.

Together, these remove a lot of "who should look at this?" and "what does this change even do?" questions.

Say it like this

"Anything under /infra needs a CODEOWNERS approval, so it'll auto-request the platform team."

Three ways of organising work on GitHub, from lightweight to full planning board.

  • Labels are coloured tags on issues and PRs: bug, docs, blocked, good first issue. Use them for type and status, and keep the set small.
  • Milestones group issues and PRs towards a goal or date, such as "v1.0 launch", and show a progress bar.
  • GitHub Projects are flexible boards and tables across many repos. Cards are issues and PRs, with columns such as Todo, In progress and Done, plus custom fields like priority or size. Automations can move items as PRs open and merge.

The common loop: an idea becomes an issue, goes onto the Project board, someone picks it up and opens a PR that says Fixes #n, and when it merges the card moves to Done on its own.

Don't over-engineer this. A small team can run happily on issues plus labels; reach for Projects when you need an overview.

Say it like this

"Label it 'blocked' and put it in the next milestone, we can't ship the release without it."

An organisation is a shared account for a group, so repos belong to the team rather than to one person.

A personal repo lives at github.com/you/project; an organisation's lives at github.com/acme/project. If the person who owns a personal repo leaves, the project goes with them, which is why teams use organisations.

Within an organisation you group people into teams (@acme/backend) and give those teams access to repos. The roles on a repo, from least to most power:

RoleCan do
ReadView and clone; comment on issues and PRs.
TriageRead, plus manage issues and PRs (labels, assign), no code changes.
WritePush branches, review and merge PRs.
MaintainWrite, plus manage the repo without sensitive settings.
AdminEverything, including settings, secrets and deleting the repo.

Principle of least privilege: give people the lowest role that lets them do their job. Most contributors need Write at most. Organisations also get owners (who control billing and membership), single sign-on options, and audit logs on paid plans.

For outside helpers, invite them as an outside collaborator on a single repo rather than adding them to the whole organisation.

Say it like this

"Give the contractor Write on that one repo as an outside collaborator, not org membership."

Most team friction comes from habits, not tools, and a few habits fix most of it.

  • Small PRs. Aim for something a reviewer can read in 15 minutes. If it's bigger, split it.
  • Describe your change. Say what and why, how to test it, and link the issue. A review request with no description is rude.
  • Self-review first. Read your own diff on the Files changed tab before asking anyone else. You'll spot leftovers.
  • Review promptly. A PR waiting for days blocks the author and invites conflicts.
  • Keep feedback kind and specific. Comment on the code, not the person. Ask questions ("what happens if this is empty?") rather than issuing verdicts.
  • Don't force-push to a branch someone is reviewing without saying so. It breaks their sense of what changed.
  • Pull often so you build on the latest main.
  • Use the PR for decisions. If it was decided in chat, write the outcome down on the PR or issue so it isn't lost.
  • Notifications: tune them (Settings, Notifications) so they don't bury you. Watching "Participating and @mentions" is a good default.

Say it like this

"This one is big, can we split the refactor from the feature so review is quicker?"

Actions run a script on GitHub's computers whenever something happens in your repo, such as a push or a new PR.

A workflow is a YAML file (a plain-text config format) in .github/workflows/. It names the event that triggers it (on), and one or more jobs, each made of steps that run on a runner (a temporary virtual machine GitHub provides). Steps either run shell commands (run) or use ready-made actions shared by others (uses).

name: CI
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm test

That file means: on every PR and every push to main, check out the code, install Node, install dependencies and run the tests. Results appear as ticks and crosses on the PR and in the Actions tab, where you can open the logs.

This is CI (continuous integration): automatically building and testing every change so problems show up before merge. Combine it with a required status check (see the protection chapter) and broken code can't reach main.

Other common triggers: schedule (a cron timer, for nightly jobs), workflow_dispatch (a manual "Run" button) and release. Public repos run Actions free; private repos get a monthly free allowance, so check the pricing page before running something heavy.

A few safety habits: set permissions: to the minimum the job needs, and treat third-party actions as code you're running, so prefer well-known ones and pin versions (check each action's page for its latest major version).

In your project

Start with one workflow that runs your tests and build on every PR. It takes ten lines and catches the "it worked until I touched that other file" problem.

Say it like this

"CI is red because the lint step failed. Check the Actions log, it's a missing semicolon."

Workflows often need passwords and keys; GitHub stores them encrypted so they never go in your code.

In Settings, then Secrets and variables, you can add:

  • Secrets: encrypted values (deploy keys, API tokens). Once saved you can't view them again, only replace them. Use them in a workflow as ${{ secrets.DEPLOY_TOKEN }}. GitHub masks them in logs.
  • Variables: plain, non-sensitive settings (a region name, a site URL), used as ${{ vars.SITE_URL }}.

An environment (such as staging or production) is a named target with its own secrets and optional protections, such as requiring a person to click approve before deploying to production.

Important limits: workflows triggered from a fork's PR don't get your secrets (otherwise a stranger could write a PR that steals them). And a workflow still shouldn't print a secret, so don't echo them.

Where possible, prefer short-lived credentials over stored keys. For major clouds, GitHub Actions can use OIDC to get a temporary token directly, so there's no long-lived secret to leak.

Say it like this

"The deploy token lives in the production environment's secrets, and prod needs a manual approval."

Pages turns a repo into a free website, and the same push-to-deploy idea works with other hosts too.

GitHub Pages hosts static sites (HTML, CSS, JavaScript) straight from a repo, at you.github.io/project or on your own domain. Switch it on under Settings, then Pages. Pick either "deploy from a branch" or "GitHub Actions" as the source; the latter is best if your site needs a build step (such as Astro, Vite or Jekyll). It's free for public repos and available for private ones on paid plans.

Pages only serves static files. If you need a server, a database or secrets at runtime, use a host that runs code.

The general pattern, on any host, is push to deploy: connect a host such as Cloudflare Pages, Vercel, Netlify or Render to your repo, and every merge to main triggers a build and a deploy. Many of them also create a preview deployment for each PR, a throwaway URL showing that exact branch, which you can share for review before merging.

Keep the deploy tied to main (not to random branches), and make sure checks pass first. Then "merge" becomes the one button that ships.

In your project

Preview URLs are great for vibe-coded projects: you see the real result of every change, and you can send the link to a friend before it's live.

Say it like this

"Merge to main and it deploys. Use the preview URL on the PR to check it first."

A release is a named, versioned snapshot of your project that people can download or depend on.

A tag labels one commit (v1.4.2). A GitHub Release sits on top of a tag and adds a title, notes describing what changed, and optional downloadable files. Create one from the Releases section on the repo page (or gh release create v1.4.2); GitHub can generate the notes from your merged PRs.

Most projects use semantic versioning (semver): three numbers, MAJOR.MINOR.PATCH.

BumpWhenExample
PATCHBug fix, nothing else changes.1.4.2 to 1.4.3
MINORNew feature, still compatible.1.4.3 to 1.5.0
MAJORBreaking change; users must adapt.1.5.0 to 2.0.0

A changelog (a CHANGELOG.md or the release notes) tells users what's new and what to watch out for. A pre-release flag (v2.0.0-beta.1) lets you publish something for testing without calling it final. If you publish a library, a release can trigger a workflow that publishes to npm, PyPI or a container registry.

A release and a deploy are different: a release names a version; a deploy puts some version on servers.

Say it like this

"It's a breaking change so that's a major bump. Tag v2.0.0 and write it up in the release notes."

Most security problems in small projects come from outdated dependencies and leaked keys, and GitHub watches for both.

The Security tab collects several free-for-public-repos tools:

  • Dependabot alerts tell you when a library you use has a known vulnerability.
  • Dependabot security updates open a PR automatically that upgrades the vulnerable dependency.
  • Dependabot version updates (configured in .github/dependabot.yml) open regular PRs to keep dependencies fresh, so upgrades stay small instead of piling up.
  • Secret scanning and push protection catch leaked keys, as covered earlier.
  • Code scanning (CodeQL) analyses your code for common vulnerability patterns and reports them on PRs.
  • Private vulnerability reporting lets people tell you about a problem confidentially instead of in a public issue.
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"

A dependency is a library your project uses; a lockfile (package-lock.json, poetry.lock) records the exact versions, and should be committed. Dependabot PRs should still be reviewed and tested; green checks are what make them safe to merge quickly.

In your project

Turn on Dependabot alerts and security updates today. It's two clicks and it's the cheapest security win available.

Say it like this

"Dependabot opened a PR for the vulnerable package, CI is green, so merge it."

AI tools can change dozens of files in seconds, and Git is how you stay in control of that.

When an assistant writes or edits code for you, the risk isn't that it's always wrong; it's that changes are big, fast and hard to follow. A few habits make this safe:

  1. Start from a clean state. Run git status. If there are uncommitted changes, commit or stash them first, so the AI's changes are the only ones in the diff.
  2. Work on a branch. git switch -c try-new-header before you start. If it all goes wrong, delete the branch.
  3. Commit after every working step. Each success becomes a save point you can return to.
  4. Read the diff before you commit. git diff or the Source Control panel. Look for deleted files, changed config, new dependencies and anything that looks like a key.
  5. Run it and test it. "It compiled" isn't "it works".
  6. If it spirals, stop and reset. git restore . discards uncommitted changes (and any new untracked files stay, so check git status); git reset --hard goes back to the last commit. A fresh start from a clear prompt beats ten rounds of patching.

Be wary of anything the assistant wants to run that you don't understand, especially commands that delete files, change history (--force, reset --hard) or install unfamiliar packages. And don't paste secrets into prompts.

Careful

Never give an AI tool your .env contents, tokens or private keys, and make sure .env is in .gitignore before you let any tool "commit everything".

Say it like this

"I committed before I let the agent loose, so if it made a mess I can just reset."

Coding agents can now open pull requests themselves, which makes the PR and its checks your main control point.

Tools such as GitHub's Copilot coding agent and Claude Code can read an issue, write code on a branch and open a PR for you to review. Treat that PR exactly like one from a new teammate: it needs a clear description, passing checks and a human reading the diff. A few practices help:

  • Write clear issues. The better the description (what, why, how you'd know it's done), the better the result. Vague in, vague out.
  • Keep tasks small. One agent task, one focused PR. Big vague tasks produce big vague diffs.
  • Let checks do the first review. Tests, lint and type checks catch a lot of AI mistakes automatically. If you don't have tests, ask for them as part of the change.
  • Review for what AI tends to get wrong: invented functions or libraries, silently deleted tests, duplicated code, hard-coded values, missing error handling and security shortcuts.
  • Protect main. Branch protection means an agent (or you) can't push there directly, and a human approval is required.
  • Limit its access. Give tokens the narrowest permissions and shortest life that work, and keep production secrets out of reach.

You can also use AI as reviewer: Copilot code review and similar tools comment on PRs. They're a useful extra pair of eyes but not a replacement for yours.

In your project

The loop that works: write an issue, let the tool do a branch and PR, read the diff, let CI run, fix or ask for changes, then merge. You stay the editor.

Say it like this

"The agent's PR touches forty files for a one-line change. Send it back and ask for a smaller diff."

The gh command lets you do GitHub things (PRs, issues, releases) from your terminal without opening the browser.

It's a separate tool from Git: Git handles commits and branches, gh talks to GitHub's website features. Install it, then sign in once with gh auth login.

gh repo create my-app --private --source=. --push
gh pr create --fill          # open a PR using your commit messages
gh pr status                 # your PRs and their checks
gh pr checkout 123           # fetch someone's PR branch to try it
gh pr merge --squash --delete-branch
gh issue create --title "Fix login bug"
gh run list                  # recent Actions runs
gh run view --log-failed     # why did CI fail?

It's especially handy for AI tooling and scripts, because commands are predictable text. Many coding agents use gh behind the scenes to open PRs and read CI results.

Say it like this

"Just run gh pr checkout and try it locally, no need to add their fork as a remote."

You don't always need to install anything: GitHub can give you a full editor in a browser tab.

  • github.dev: press . on any repo page for a lightweight VS Code in your browser. Great for quick edits and reading code; it can't run your app.
  • Codespaces: a full cloud development machine for your repo, with a terminal, your tools installed and the app running. Open one from the Code button. There's a monthly free allowance, and they stop automatically when idle, but remember to delete ones you don't need.
  • Dev containers: a .devcontainer/devcontainer.json file in the repo defines the setup (languages, extensions), so everyone's environment is identical. It also removes "works on my machine" for new teammates.

The web editor on a file page (pencil icon) is fine for fixing a typo: it will offer to commit on a new branch and open a PR in one go.

Say it like this

"Spin up a codespace instead of installing everything, the devcontainer has the whole setup."

Putting it together: the same way of working, said three ways.

Engineers describe a workflow in order, naming each step and its safeguard. Here's a solo project at three levels of detail.

The one-liner:

"Everything goes through short-lived branches and pull requests, CI runs the tests, and merging to main deploys."

The thirty-second version:

"Main is protected, so I never commit to it directly. For each change I branch off, commit in small steps, push and open a PR. The PR runs the build and tests through GitHub Actions and gets a preview deployment. I read my own diff before merging, squash-merge it and the branch deletes itself. Merging to main deploys to production."

The team answer, if someone asks about safety:

"Direct pushes and force pushes to main are blocked, a PR needs one approval and green checks, CODEOWNERS routes sensitive paths to the right reviewer, secrets live in environment settings rather than code, Dependabot and secret scanning are on, and AI-authored PRs go through the same review as anyone's."

Notice the pattern: where work happens, how it's checked, how it lands, how it ships, and what stops mistakes. That structure works for any team.
